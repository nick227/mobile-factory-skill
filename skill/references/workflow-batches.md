# Documentation decision batches (opt-in)

After Requirements is complete, enable with:
```sh
node scripts/factory.mjs workflow batch init --project <dir>
node scripts/factory.mjs workflow next --project <dir>
node scripts/factory.mjs workflow batch set classification --project <dir> --file selection.json
```

Classification (MR 2): run `catalog apps` to list controlled application archetypes, then `catalog app <id>` to inspect its deterministic suggestions. Save only `{ "type": "tracker" }` (or another registered ID). After selection, `workflow next` provides suggested object, capability and page IDs for *later* batches; these are not yet resolved or implemented. Application archetypes are separate from the six visual Monad page archetypes.

Objects (MR 3): select **core object namespaces** as compact IDs, optionally declaring typed links. Example: `["program",{"id":"activity","relations":[{"to":"program","kind":"belongs-to"}]}]`. Link kinds: `belongs-to`, `has-many`, `references`. Only declared object IDs are valid targets; duplicate IDs, invalid relations, and circular `belongs-to` graphs fail before any state is saved. `workflow objects --project <dir>` resolves stable data/event/control/display namespaces. The next Functionality batch receives the resolved object contracts, but must independently select capability IDs; object declarations never imply working functionality.

Functionality (MR 4): use `catalog capabilities` and `catalog capability <operation>` to inspect registered semantic operations. Select exact IDs such as `["activity.search","activity.filter","activity.complete"]` for previously declared object namespaces. `auth.basic` is the only system-scoped capability. Requires and conflicts are validated against the complete selection (for example `filter` requires `search`; `read-only` conflicts with mutations). `workflow functionality --project <dir>` resolves deterministic event, control and display IDs for downstream page planning. These IDs represent **planning contracts only**, not implemented controls, authentication, or handlers; unsupported behaviors must not be claimed as working.

Capability implementation resolution (engineering MR 1): run `catalog implementations` and `workflow capability-coverage --project <dir>` after selecting functionality. Planning IDs and runtime behavior are different: `local-mock` means local presentation behavior only, `policy` means selection validation, and `missing-adapter` identifies functionality the generator cannot implement (currently authentication and real checkout). No current entries are certified as production-ready or device-verified. This inventory is advisory in MR 1 to preserve existing workflows; later engineering contracts will govern authorized exceptions. The resolver MUST NOT treat a matching vocabulary ID as proof of production functionality.

Pages (MR 5): run `catalog pages --type <app-type>` to inspect page pattern IDs or `catalog page <id>` for exact contracts. At the Pages batch, `workflow next` shows archetype defaults and capability coverage diagnostics; select a compact array of registered page IDs. `workflow pages --project <dir>` resolves routes, bound object namespaces, navigation links, and covered capability IDs. Validation rejects wrong-app patterns, duplicate routes, missing root, unreachable screens and uncovered capabilities; `auth.basic` requires both `auth.login` and `auth.register`. Page definitions and auth behavior are **planning-only**, not generated JSX, real authentication, or working navigation yet. For now the catalog binds page object roles by declaration order (0 = first object, 1 = second); later composition may make these semantic bindings explicit.

Composition (MR 6): select exactly one compact contract per chosen page ID, including `kind`, a compatible Monad `archetype`, and `bindings` with field IDs. Collections use `{title,description?,search?,filter?,media?}`, detail pages use `{heading,hero? (required for glance-dashboard),facts?,body?,progress?,unit?,media?}`, forms use `{fields:[...]}`, and settings use `{groups:[...]}`. Optional `navigation:[{to:"page-id",placement:"select|primary|header|action"}]` binds only catalog-authorized navigation; `actions:[{id:"object.operation",placement:"primary|action",field?:"boolean-field"}]` binds selected local-state capabilities. The compiler refuses unbound selected functionality, invalid field IDs, ambiguous primary actions, missing pages, incompatible subjects or routes. `workflow composition --project <dir>` returns a **draft** assembler-validated AppSpec with synthetic fixtures. It is not ready for approval or production until Content & Editorial replaces fixtures and the next MR audits the final revision. Authentication is not simulated as real auth and is rejected by the presentation compiler.

Content & Approval (MR 7): supply `{ "pages": {"tracker.home":{"title":"Today"}}, "data": {"activity":[{"id":"activity-1","name":"Example",...}]} }` using exactly the compiled page IDs and object fields. All pages require titles; all bound collections require nonempty realistic records with unique IDs and correct types. Optional page copy includes `subtitle`, `primary`, `header`, `empty`, `fields` and `actions`; `design` accepts existing AppSpec design axes. No synthetic fixtures or unmatched fields can pass. Use `workflow spec --project <dir>` to inspect the final validated AppSpec and SHA-256. In `review`, supply `{ "passed": true, "evidence": "...", "specHash": "<hash reported by workflow spec>" }`. **This is an AI/technical review, not user approval.** After sharing the exact revision and spec for explicit confirmation, run `workflow confirm --project <dir> --quote "<user's actual approval words>"`, then `blueprint audit` and `blueprint approve`. Never fabricate user consent. Approved batch blueprints pin the executable AppSpec hash, not the legacy screen projection; changing upstream selections invalidates approval.

Generation (MR 8): after explicit user confirmation and `blueprint approve`, run `node scripts/factory.mjs factory generate --project <dir>`. This validates the exact revision-locked SHA-256 AppSpec, scaffolds the Expo template and approved UI source, then uses the existing deterministic assembler to emit all routes/Monad screen contracts. `--dry-run true` previews the generated file list without changing the destination. Repeat on the same approved input to verify idempotency. Existing generated route files are updated only when owned by the assembler; hand-edited files cause a non-destructive conflict. The command performs no AI reasoning, no JSX composition and no network dependency installation. Run `pnpm install` and device/type checks separately after generation.

Engineering exceptions (engineering MR 2): optionally supply `engineering:[{id,requirement,strategy,reason,contract:{inputs:[],outputs:[],events:[]},acceptance:[],platforms?:['ios','android'],page?}]` within the existing **content** batch; no additional batch or AI round trip is required. Strategies are `extension`, `adapter`, or `ejection` (requires an existing selected page). The factory derives file scope (`src/extensions/<id>/**`, `src/adapters/<id>/**`, or the selected route), rejects duplicate IDs/routes, and requires a real requirement, interface and acceptance test. `workflow engineering --project <dir>` shows the normalized planned work. If exceptions exist, `workflow spec` exposes both the AppSpec hash and a separate `blueprintHash` including the contracts. Review must include both hashes, and explicit user confirmation is tied to the blueprint hash. Normal apps without exceptions retain their previous hash and approval behavior. Until controlled construction is installed, generation refuses blueprints with pending exceptions, rather than pretending those features work.

Controlled Construction (engineering MR 3): `engineering prepare --project <dir>` accepts **only** an explicitly approved blueprint with contracts, generates the standard Expo shell through the existing deterministic compiler, invokes the Assembly Ejection Protocol for authorized ejected screens, and writes a baseline under `.factory/engineering-authorization.json`. No custom functionality is considered implemented yet. `engineering tasks --project <dir>` returns bounded agent work orders with exact source and test scopes. Agents must produce code only within those scopes; `engineering verify --project <dir>` detects new/modified/deleted files outside them, missing implementation files, missing tests, and untouched ejection placeholders. Run `engineering verify --run-checks true` after dependency installation to execute Node extension tests and `pnpm run typecheck`. The command never approves deployment or claims device verification; each contract still requires explicit manual acceptance evidence. Existing approved apps without exceptions retain ordinary `factory generate` behavior; that ordinary command remains blocked while custom work is pending.

Use **one batch at a time**. Read only the indicated batch's existing upstream selections and relevant catalog. Save the selection as JSON; run `workflow next` again. Do not combine classifications, objects, capabilities or pages into one agent task.

Order: `classification` → `objects` → `functionality` → `pages` → `composition` → `content` → `review`.

Selections live in `.factory/project.json` under `batches.selections`. Repeating an identical selection is a no-op. Changing an earlier one removes downstream selections, invalidates approval and stales dependent completed screen work; completed upstream selections remain intact.

**Scope:** MR 8 turns approved batch blueprints into Expo presentation apps with one deterministic command. Legacy non-batch projects retain their existing scaffold/assemble flow. The command generates source only; runtime/device verification and publishing remain separate quality gates. Do not claim the current batch contract is sufficient to produce an executable app. Existing projects without `batches` continue unchanged.
